Critical review — methodological flaw found and fixed (not just text)
====================================================================================

CONTEXT: during a deliberate critical review of the manuscript (explicitly
requested to stress-test the work before any journal targeting),
verification of the hypothesis "the set 'stale in 144' should be a
subset of the set 'stale in 138'" (expected monotonicity property).

CONSISTENCY TEST RESULT
------------------------
Stale in 138: 369
Stale in 144: 105
Stale in BOTH: 87
Stale in 144 ONLY (violates expected monotonicity): 18  <-- ANOMALY
Stale in 138 ONLY: 282

DIAGNOSIS (verified directly on the raw files, not assumed)
----------------------------------------------------------------------
awk -F'\t' '$1==49283799' gdc_dbsnp144_chr20_full.tsv gives TWO lines:
  49283799  G  C  rs238202
  49283799  G  C  rs386421256

The dbSNP144 bundle REALLY contains two distinct records at the
EXACT SAME position+allele: the current ID (rs238202) AND an
as-yet-unresolved duplicate submission (rs386421256, which will be merged into
rs238202 on 2015-07-01, i.e. AFTER the date of the dbSNP144 snapshot used, 2015-06-03).

My original script (Python dict `{(pos,ref,alt): id}`) silently
overwrote the first line with the second -- arbitrarily keeping one of the two IDs
depending on the order of appearance in the file, never flagging the conflict.
Verified on both bundles: **16,830 conflicting keys in dbSNP138**,
**33,994 in dbSNP144** (across the whole file, not just the panel).

FIX APPLIED (scripts/check_bundle_staleness_FIXED.py)
------------------------------------------------------------------
Replaced the dict with a `defaultdict(set)` that keeps ALL IDs seen
for each (pos,ref,alt) key, then a 4-outcome classification: current only /
stale only / BOTH at once (new "ambiguous" category) / absent.

CORRECTED RESULT (definitively supersedes the results/10 figures)
--------------------------------------------------------------------------
                                  dbSNP138 (2014)    dbSNP144 (June 2015)
Absent from bundle                     19                  31
CURRENT ID only                    2,506 (86.6%)      2,725 (94.16%)
STALE ID only                        369 (12.75%)        75 (2.59%)
**AMBIGUOUS (both present)**              0             **63 (2.18%)**

=> **dbSNP138 is completely unaffected by the fix** (0 ambiguous cases in
   this bundle for this panel) -- the 12.75% figure was already correct and
   robust.
=> **dbSNP144 is corrected**: the "clean" stale rate drops from
   3.63% to 2.59%, BUT a new category appears -- 2.18% of
   variants are in an AMBIGUOUS state where the bundle lists the
   current identifier AND a stale identifier SIMULTANEOUSLY for the same position and
   the same exact allele. If stale+ambiguous are combined as "at risk for a
   naive consumer" (2.59%+2.18% = 4.77%), the real risk of bundle 144
   is actually SLIGHTLY HIGHER than the "clean" figure suggests.

INTERPRETATION -- this strengthens the paper, does not weaken it
------------------------------------------------------------------
This is not just a bug fix: it is a substantial additional finding. A
reference bundle can be "stale" in TWO distinct ways:
  1. Classic: it only knows the old ID (the dbSNP138 case, 12.75%).
  2. Ambiguous: it lists BOTH IDs simultaneously for the same variant,
     because the snapshot was taken during the duplicate's resolution
     window -- a naive consumer doing an exact join on
     (position, allele) -> ID would get a NON-DETERMINISTIC result
     (depending on line order in the VCF file, or on the downstream
     tool's implementation), which is arguably WORSE than plain
     staleness since the behavior is not even reproducible.

This second failure mode is new and was not anticipated -- exactly
the kind of finding a critical review is supposed to surface, and exactly
the kind of honest result (positive AND negative) that already characterizes Paper A/B.

ACTIONS TAKEN
--------------
- Manuscript (Section 5.6, Figure 2) updated with the new
  "Ambiguous (duplicate at site)" category and the corrected figures.
- Section 4.4 (protocol) expanded to document the multi-ID handling.
- No change to Section 5.5 (bundle 138) -- verified unaffected.

OTHER VERIFICATIONS FROM THE CRITICAL REVIEW (same data, positive checks)
-----------------------------------------------------------------------------
1. **Statistical significance** (previously absent): Fisher's exact test
   on the 2x2 table (369/2506 vs 75/2725) -> odds ratio 5.35,
   **p = 1.07x10^-49**. The 138 vs 144 difference is extremely significant,
   not a chance effect. Added to Section 5.6.

2. **Genomic clustering** (could the 369 stale positions in dbSNP138
   be concentrated in a single repetitive/poorly-curated region, which would
   weaken the result's generality?): NO -- the 369
   positions cover nearly the entire length of chr20 (130,329 to
   63,061,840), touching 54 of ~64 1Mb bins, the densest bin holding
   only 31 (8.4%). Robust result, not a local artifact. Added
   to Section 5.6.

3. **"Independently administered identifier system" wording corrected**:
   dbSNP AND NCBI Taxonomy are both maintained by NCBI -- this is
   NOT a test between two independent organizations. Reworded in Section
   6.1 to clarify that it is the curation LOGIC (data models,
   submission/deduplication pipelines, merge triggers) that is
   independent, not the organization -- avoids an easy reviewer objection.

CRITICAL REVIEW CONCLUSION
------------------------------
A real methodological flaw found and fixed (duplicate keys in the
bundles), turned into an additional finding rather than hidden.
Two robustness checks added (significance, spatial
dispersion) that reinforce the central result's solidity. An
overclaimed statement corrected before a reviewer could catch it. This is exactly
the level of rigor expected before targeting a journal.
