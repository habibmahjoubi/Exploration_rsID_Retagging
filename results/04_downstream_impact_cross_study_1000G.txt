"Downstream impact" test #1: widely-cited historical resource (1000 Genomes Phase 3)
=====================================================================================

Hypothesis tested: an old but still actively used/cited resource
(1000 Genomes Phase 3, released 2013) would still carry the OLD rsID (pre-merge)
for positions where dbSNP has since merged the identifier — a naive
rsID join between this resource and a modern annotation would fail silently.

Source tested: ALL.chr20.phase3_shapeit2_mvncall_integrated_v5a.20130502.genotypes.vcf.gz
(NCBI mirror, 1000 Genomes Project, assembly **GRCh37/b37** confirmed in the header —
note, different from the GRCh38 used for the rest of this exploration).

Method: direct search for the 8 old rsIDs (most recently known merges,
2014-2016) via string match on the VCF's ID column (independent of the
coordinate system, unlike position-based matching).

RESULT: NEGATIVE (honest, not hidden)
----------------------------------------
None of the 8 searched-for old rsIDs (rs112456685, rs78807921, rs74969895,
rs73608953, rs868251420, rs117776407, rs386421256, rs80132470) appear in
the 1000G Phase 3 file. However, 4 of the corresponding CURRENT rsIDs
(rs201556, rs200359, rs199784, rs238202) already appear there, as of 2013.

IMPORTANT INTERPRETATION (refines the hypothesis rather than confirming it as-is):
By dbSNP convention, a merge always retires the HIGHER-numbered rsID into the
LOWER one ("rsHigh merged into rsLow"). The candidates we tested all have an
"old" rsID numerically higher than the surviving current rsID. A resource
established BEFORE this high rsID was created/submitted (or that simply always
used the dominant low rsID) could not, by construction, ever have cited the
identifier that would later be merged — it was therefore never exposed to the risk.

=> The "naive join broken by an old rsID" risk is not generic to
   "any old resource": it can only manifest for a resource that actually
   cited the (higher, more recent) rsID that will later be merged —
   typically a publication/submission close in time to that identifier's
   creation, before dbSNP discovers the duplicate and merges it. This is NOT
   the case for 1000G Phase 3 for the 8 candidates tested here.

Limitation: n=8 candidates only, and b37 coordinate system (search done by
text ID, so independent of coordinates, but 1000G's own position<->ID mapping
remains in b37 if one ever wants to verify beyond the raw ID).

NEXT TEST TO RUN for a more solid confirmation/refutation: look for
candidates where the OLDER rsID (numerically lower, or submitted early) was
merged INTO a more recent rsID -- rarer given the "high->low" convention,
but not impossible (can happen when two old clusters merge into each
other and dbSNP chooses to keep the second one as the reference for some
technical reason) -- or test directly on a panel of GWAS
publications (gwas-catalog-associations, EBI) that cite rsIDs which are by nature younger/closer
to their merge date.
